# xfade v0.11.0

Security hardening and verifiable releases. This release closes credential
forwarding paths in the local proxy, hardens loopback access and secret-bearing
files, verifies downloads, and introduces signed release provenance.

---

## Security hardening

- Inbound credentials (`x-api-key`, `api-key`, `x-goog-api-key`,
  `x-auth-token`, proxy authorization, and cookies) are stripped before a
  request reaches any upstream. Each route receives only its own configured
  credential, including during failover.
- Loopback listeners reject foreign `Host` and `Origin` headers to defend
  against browser cross-site requests and DNS rebinding.
- Non-loopback listeners now require an auth token. Both OpenAI-style
  `Authorization: Bearer` and Anthropic-style `x-api-key` client tokens work.
- Daemon auth tokens no longer appear in launchd/systemd process arguments;
  they are read from an owner-only file.
- Client configs, backups, the file secret backend, and daemon metadata are
  created atomically with owner-only permissions on Unix.
- `xfade config` no longer reveals an API-key prefix.

## Verified distribution

- The installer and `xfade self-update` verify the selected archive against
  the release's `SHA256SUMS` and fail closed.
- `SHA256SUMS` is signed keylessly by the release workflow with Sigstore; the
  signature bundle is published alongside each release.
- GitHub build-provenance attestations are generated for every release asset.
- All third-party actions in the release workflow are pinned to immutable
  commit SHAs.

Verify a downloaded CLI archive:

```bash
scripts/verify-release.sh v0.11.0
```

See [RELEASE.md](../../RELEASE.md#signing) for direct Cosign and GitHub
attestation commands.

## Session handover

`xfade handover [--copy|--raw]` creates a compact Markdown brief from the most
recent session and current Git state. `xfade <tool> --handover` captures the
same brief before launching a tool. This is an initial local implementation;
automatic prompt injection and project-scoped session selection remain future
work.

## Compatibility

- Clients reaching the proxy through a non-loopback hostname (for example,
  from a container through `host.docker.internal`) must configure both
  `--host` and an auth token.
- Re-run `xfade serve install` to migrate an existing daemon token out of
  launchd/systemd arguments.
- Existing client config files are rewritten as owner-only the next time
  xfade updates them.
